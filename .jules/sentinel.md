## 2025-02-28 - Restrict Express Middleware Defaults
**Vulnerability:** Overly permissive defaults on `express.json()` and `cors()` in Express setup.
**Learning:** By default, `express.json()` allows unlimited payload sizes, which can lead to DoS attacks via memory exhaustion. Similarly, `cors()` without options allows all origins, which can lead to unauthorized cross-origin requests.
**Prevention:** Always configure `express.json({ limit: '...' })` and define a strict `origin` array/function for `cors()`.
## 2025-03-09 - Express Rate Limiting Behind Reverse Proxy IP Spoofing
**Vulnerability:** The application implements an IP-based rate limiter to protect sensitive endpoints (e.g. `/api/chat`). However, without explicitly configuring Express to trust the reverse proxy (via `app.set('trust proxy', 1);`), the `req.ip` property resolves to the internal IP of the reverse proxy itself (like Cloud Run) instead of the actual client IP. This means the rate limit is incorrectly applied globally across all clients sharing that proxy connection, causing legitimate users to be blocked once the limit is reached by the collective sum of requests. Conversely, in certain configurations, attackers might bypass rate limiting or spoof their IP if headers aren't handled correctly by the framework when it doesn't trust the proxy.
**Learning:** Framework-level middleware and properties like `req.ip` or rate limiters that depend on IP addresses rely on proxy headers (like `X-Forwarded-For`). Express ignores these headers by default for security reasons to prevent IP spoofing from direct connections. When deployed behind a trusted reverse proxy, we must explicitly tell Express to process these headers.
**Prevention:** Always configure `app.set('trust proxy', 1);` (or specify an exact subnet/number of proxy hops) immediately after initializing an Express application when deploying behind load balancers or reverse proxies (such as GCP Cloud Run, AWS ELB, Heroku, or Nginx).
